Exchange Online Protection Baseline

A documentation-led, evidence-oriented example for an Exchange Online administrator journey

Example only: This repository is not an official Microsoft product or service. It does not provision a tenant, establish licensing, grant access, or certify production readiness. Every deployment requires independently approved inputs, current entitlement evidence, least-privilege access, and change authorization.

Supported scope

The active workflow evaluates a versioned Exchange-only profile for a Worldwide tenant. It uses Microsoft-managed Standard and Strict preset security policies without copying or modifying their individual settings.

  • Standard preset for the approved broad recipient population
  • Strict preset for an approved priority-user group
  • Exchange Online hardening and evidence collection
  • Fail-closed input, entitlement, approval, and evidence contracts

Protection profiles

Standard

Microsoft's recommended baseline profile for broad recipient coverage.

Strict

A more aggressive Microsoft-managed profile for selected high-value targets or priority users.

Automated Investigation and Response, Threat Explorer, and Attack Simulation Training are separate Microsoft Defender for Office 365 Plan 2 capabilities. Assigning Strict does not enable them.

What this repository does not claim

  • It does not reproduce Microsoft-managed preset values in local templates.
  • It does not provide a generic detect-only mode for Standard or Strict presets.
  • It does not infer entitlement from a suite name or declare that capabilities have no additional licensing cost.
  • It does not certify DNS, identity, licensing, client, Purview, or other externally owned readiness.
  • It does not validate sovereign-cloud or hybrid deployment paths.

Supported configuration contract

The legacy browser configuration generator has been removed

The former generator emitted a quarantined custom-policy format and could not be used with the active schema. Use the versioned configuration, manifest, schema, and parameter contracts below.

Active artifacts

  • exchange-only.v1.json - retained Exchange control configuration
  • exchange-only.schema.v1.json - closed validation schema
  • exchange-only.manifest.v1.json - retained controls and explicit exclusions
  • parameters.exchange-only.sample.json - synthetic input example, not approval

Input rules

  • Keep resolved tenant input outside source control.
  • Replace every __ADMIN_REQUIRED:... token with independently approved data.
  • Supply current tenant- and recipient-bound entitlement evidence.
  • Bind domain inventory, recipient scope, approvals, exceptions, and external handoffs to named owners and evidence references.
  • Stop on missing, stale, malformed, unresolved, or scope-mismatched input.

Customization boundary

Virtually all individual settings in Standard and Strict preset security policies are Microsoft-managed and cannot be customized. Administrators can manage supported recipient scope and exclusions. Custom policies require a documented business need and do not override an applicable Strict or Standard preset because presets have higher precedence.

Repository values identify their provenance as a Microsoft recommendation, local policy, or approved exception. A local choice must never be represented as a Microsoft default.

Exchange administrator journey

Resolve inputs, preview approved scope, apply through change control, and verify frozen evidence

Runtime

  • PowerShell 7.6 or later
  • ExchangeOnlineManagement 3.10.0 or later
  • Worldwide tenant (O365Default)
  • Approved Exchange identity with least-privilege access
  • Protected input and artifact locations outside source control

Pin and validate the exact module version used by the approved change. Do not rely on an unqualified "PowerShell 7+" prerequisite.

Least privilege

Use the narrowest supported permissions for each operation. Preset policies can be managed through applicable Defender Unified RBAC permissions or Exchange Online Organization Management or Security Administrator role groups.

Global Administrator is highly privileged and should be limited to emergency scenarios or cases where a narrower role cannot be used.

Offline input validation and plan

From samples\contoso-exchange-online-managed-service, start with the synthetic parameter file only for offline structure validation:

.\scripts\Deploy-ExchangeOnlineBaseline.ps1 `
    -ParameterPath .\config\parameters.exchange-only.sample.json `
    -SkipConnection

The unmodified sample must stop because its licensing handoff is unverified. With approved input, this command produces an Exchange-only plan and configuration hash; it makes no changes and is not a signed approval artifact.

Approved change

  1. Resolve all owner handoffs and administrator inputs.
  2. Validate the closed schema, manifest, domain inventory, entitlement, and recipient matrix.
  3. Initialize Standard and Strict preset objects in the Microsoft Defender portal.
  4. Create an immutable preview bound to exact before-state and approval.
  5. Apply only adapters explicitly supported by the approved-change contract.
  6. Recollect the complete evidence matrix and verify the exact configuration hash.

Recovery

Rollback uses before-state captured by the approved-change workflow and restores only settings covered by reviewed adapters. Never recreate Microsoft-managed preset backing policies from serialized PowerShell output.

After recovery, recollect and verify the complete evidence matrix. Configuration recovery cannot reverse messages already delivered, quarantined, or otherwise processed.

Government and sovereign clouds

Microsoft Defender for Office 365 is available in GCC, GCC High, and DoD with environment-specific portals, licensing, and capability differences. This repository's active journey is limited to Worldwide tenants and has not validated sovereign-cloud or hybrid endpoints, authentication, licensing, or feature behavior.

Do not use this microsite as evidence that GCC High, DoD, or hybrid deployments are supported.

Validation and evidence

Repository tests establish repository behavior; Microsoft documentation establishes product behavior

Static baseline guardrails

Invoke-Pester `
    .\samples\contoso-exchange-online-managed-service\tests\SecureBaseline.Tests.ps1

These tests inspect shipped configuration. They do not certify a live tenant.

Microsite content guardrails

Invoke-Pester `
    .\samples\contoso-exchange-online-managed-service\tests\unit\MicrositeContent.Tests.ps1

The content tests reject legacy scripts, obsolete schemas, detect-only preset claims, and other unsupported concepts.

Evidence contract

Live collection must use the same configuration, parameters, entitlement handoff, recipient matrix, manifest, and approval that governed the change. Pass, NotEntitled, ApprovedException, Fail, and Error remain distinct. Externally owned readiness remains unverified until its accountable owner supplies admissible evidence.

Frequently asked questions

Does preview create a detect-only mail-flow mode?

No. The supported plan and approved preview describe proposed administrative changes. Standard and Strict presets enforce their documented actions when assigned. Microsoft Defender evaluation is a separate feature and is not configured by this workflow.

Can I tune Standard or Strict thresholds?

No. Virtually all individual preset settings are Microsoft-managed. Manage supported recipient scope and exclusions instead. A custom policy does not override an applicable Strict or Standard preset.

Does Strict include AIR?

No. Strict is a Microsoft-managed protection profile. AIR and other advanced investigation capabilities are separate Plan 2 features and require applicable tenant and recipient entitlement.

Are all capabilities included at no extra cost?

No general cost claim can be made. Required licensing depends on the capability and every recipient who benefits from it. Verify current tenant service plans and recipient assignments; do not infer entitlement from a suite display name.

How should false positives be handled?

Submit legitimate messages, URLs, or attachments to Microsoft first. When Microsoft filtering caused the block, the service can create the applicable temporary allow entry. Entity type controls behavior and expiration. Broad or permanent sender allows must not replace authentication fixes, correct scope, or verdict review.

The active configuration prohibits permanent allow entries and requires owner, ticket, timestamps, expiry, and justification for governed entries.

Does this workflow support GCC High or DoD?

No validated support is claimed. The active administrator journey is Worldwide-only. Sovereign and hybrid environments require a separately reviewed and tested journey.
